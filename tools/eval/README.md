# tools/eval — оценка качества RAG-ответов (Волна 5, пункты 5.2–5.3)

Харнесс меряет **качество ответа** (генерация + контекст), а не ретрив.
Ретрив-харнесс — отдельный и уже существует: `test/eval/eval.ts` (recall@10 по
`/api/vault/search/*`). Одно другое не заменяет: `eval.ts` отвечает на вопрос
«нашли ли нужный документ», этот — «правильный ли получился ответ».

> **Абсолютным цифрам судьи не доверять.** Метрики выставляет та же LLM
> (GigaChat), что генерирует ответы. Значение «faithfulness 0.78» само по себе
> не значит ничего: судья плохо откалиброван, чувствителен к формулировке
> промпта и шумит между вызовами. Осмысленна только **дельта между двумя
> прогонами** этого же харнесса на том же golden-set и той же версии судейских
> промптов (`metrics.PROMPT_VERSION`). Это же предупреждение печатается в шапке
> каждого отчёта и каждой diff-таблицы.

## Где мы сейчас: baseline так и не снят

План предполагал baseline до Волны 3, но живого прогона не было ни разу — все
пять волн уехали в код без замера. Практическое следствие: **первый прогон уже
не покажет дельту одной волны**. Он покажет абсолютную картину системы «после
всего» — а абсолютным цифрам судьи верить нельзя (см. дисклеймер выше). Поэтому
первый отчёт стоит воспринимать как **точку отсчёта, а не как оценку**: он ни
хорош, ни плох, он просто фиксирует состояние, относительно которого будут
меряться следующие изменения.

Что с этим делать:

1. Снять первый прогон сразу после развёртывания текущей версии — с метками
   вроде `--label after-w5`. Это и есть новый baseline.
2. Прочитать не средние, а **таблицу по парам** и колонку «чанк найден»
   (`retrieval_hit`): она достоверна без судьи и сразу делит проблемы на
   «не нашли» и «нашли, но ответили плохо».
3. Дальше сравнивать только `--compare` двух прогонов на одном и том же
   `golden.jsonl` и одной версии судейских промптов.

**Полнота перечислений меряется отдельно.** Ни одна из четырёх судейских метрик
не видит неполный СПИСОК: ответ, назвавший 3 модели из 7, полностью faithful,
релевантен и опирается на контекст. Поэтому есть `item_recall` — детерминированный,
без вызова судьи, считается только по парам с полем `expected_items`. В наборе
таких пар восемь (шесть с префиксом `fb…` плюс `x24`/`x29`, куда `expected_items`
переехали при слиянии дублей; эталоны взяты из разобранного пользовательского
фидбека). У остальных метрика даёт `None` и в среднее не входит.

**A/B без пересборки.** Ручки грейдера (`rag.grader_threshold`,
`rag.grader_keep_top`, `rag.grader_enabled`, `rag.condense_enabled`) и ширина
ретрива (`rag.rerank_candidates`) правятся прямо из настроек UI и хранятся
пер-пользовательски. Значит, сравнение двух конфигураций делается так: прогон →
поменять ручки в UI → прогон с другой меткой → `--compare`. Ни образ
пересобирать, ни под перезапускать не нужно. В server-режиме обе метки надо
гонять **под одним и тем же токеном** — конфиг привязан к нему.

## Зависимостей нет

Только стандартная библиотека + `httpx` (уже в `cognivault-ui/requirements.txt`).
`gigaragas` **не используется** и ставить его не нужно: закрытый контур,
карантин SberOSC. Метрики и русский сегментатор предложений — свои
(`metrics.py`), NLTK не нужен. Для тестов дополнительно нужен `pytest`
(dev-only, как и в `cognivault-ui/tests`).

## Файлы

| Файл | Назначение |
|---|---|
| `gigachat_client.py` | минимальный mTLS-клиент `chat/completions` (без стриминга) + устойчивый разбор JSON из ответа модели |
| `gen_golden.py` | генератор golden-set: корпус → фрагменты по заголовкам → пары «вопрос / эталон» |
| `metrics.py` | четыре судейские метрики + `item_recall` (полнота перечисления, без судьи), русский сегментатор предложений, агрегация |
| `run.py` | прогон golden-set через живой UI-API, отчёты `report-<label>.{json,md}`, `--compare` |
| `tests/` | офлайн-тесты (pytest + `httpx.MockTransport`) |

## Запуск из UI (проще всего)

В настройках, раздел **«Оценка качества ответов»**: выберите встроенный набор
или загрузите собственный `.jsonl` / `.xlsx`, задайте метку и число пар, затем
нажмите кнопку запуска. Excel должен содержать столбец `Вопрос агенту`, `Вопрос`
или `question`; столбцы `Кейс` / `category` и `ground_truth` необязательны.
Загруженный файл нормализуется в JSONL и хранится в каталоге данных текущего
пользователя. Готовые JSON-, Markdown-отчёты и полный лог скачиваются в том же
разделе настроек.

Прогон идёт в фоне на сервере — страницу можно закрыть; лог виден в окне,
готовые отчёты скачиваются оттуда же ссылками.

Раздел появляется, только если харнесс есть в образе. Прогон идёт под токеном и
настройками нажавшего — иначе A/B двух конфигураций был бы бессмысленным, ручки
грейдера хранятся пер-пользовательски. Параллельные прогоны запрещены: они
дрались бы за лимит модели и за один файл отчёта.

Начните с `limit = 5` — убедиться, что судья отвечает; на нуле прогоняется весь
набор (45 пар, ~180 обращений к модели, порядка полутора часов).

## Запуск из консоли (если UI недоступен)

Харнесс **уже лежит в образе UI** — в `/srv/cognivault-ui/eval`. Класть файлы в
под не нужно: снаружи закрытого контура недоступны ни UI, ни mTLS-эндпоинт
судьи, а прав на `kubectl cp` может не быть. Зависимостей сверх уже
установленных нет — только stdlib и `httpx`.

Судья читает `GIGACHAT_BASE_URL` / `GIGACHAT_CERT_PATH` / `GIGACHAT_KEY_PATH` из
окружения — в поде они проставлены, настраивать нечего. В GigaChat он ходит
НАПРЯМУЮ, а не через KitAI: оценивать систему той же моделью, которая в ней
отвечает, — плохая идея, и так судья не зависит от смены провайдера чата.

```bash
NS=ci05490208-oasis-cognivault
POD=$(kubectl get pod -n $NS -l app.kubernetes.io/name=cognivault-ui -o name | head -1)

# Пробный прогон на пяти парах — убедиться, что судья отвечает
kubectl exec -n $NS "$POD" -- env COGNIVAULT_UI_TOKEN='<ваш токен>' \
    python3 eval/run.py --label smoke --limit 5 \
      --rag-log /data/rag_log.jsonl --out-dir /data/eval-reports

# Полный прогон = новая точка отсчёта
kubectl exec -n $NS "$POD" -- env COGNIVAULT_UI_TOKEN='<ваш токен>' \
    python3 eval/run.py --label after-w5 \
      --rag-log /data/rag_log.jsonl --out-dir /data/eval-reports
```

`--ui-url` не нужен: дефолт `http://localhost:8787` — это и есть свой же процесс.
`COGNIVAULT_UI_TOKEN` — тот же токен, которым вы ходите в UI: настройки привязаны
к нему, и обе метки A/B надо гонять под одним и тем же.

Отчёты пишутся в `/data/eval-reports` (это `emptyDir` — заберите до перезапуска
пода). Забрать без `kubectl cp` можно так:

```bash
kubectl exec -n $NS "$POD" -- cat /data/eval-reports/report-after-w5.md  > report-after-w5.md
kubectl exec -n $NS "$POD" -- cat /data/eval-reports/report-after-w5.json > report-after-w5.json
```

То же самое из вкладки **Terminal** в консоли OpenShift: команда без
`kubectl exec -n $NS "$POD" --`, а отчёт прочитать через `cat` и скопировать
из окна терминала.

Сколько это стоит: 45 пар × ~4 судейских вызова ≈ 180 обращений к GigaChat.
Прогон идёт **в один поток** (`--concurrency 1`, дефолт), по медиане ~1 минута на
пару — то есть порядка полутора часов на полный набор. Не поднимайте это число,
не проверив отчёт: у судьи на контуре фактически один слот, и второй
одновременный запрос получает 429 сразу. Прогон `baseline` шёл в два потока и
потерял 95 судейских вызовов из 188 — по чередующемуся принципу «сэмпл целиком
или ничего». Сколько их не вернулось, теперь пишется в шапке отчёта.

## Порядок работы

```bash
# 0. Поднять стек: бэкенд CogniVault + Qdrant + cognivault-ui, вольт проиндексирован.
#    Проверить, что чат в UI отвечает с включённым RAG.

# 1. Посмотреть, сколько фрагментов даёт корпус (без вызовов GigaChat)
python3 tools/eval/gen_golden.py --dry-run --limit 40

# 2. Сгенерировать golden-set (≈2 пары на фрагмент → 40 фрагментов ≈ 80 пар)
python3 tools/eval/gen_golden.py --out tools/eval/golden.jsonl --limit 40 --seed 42

# 3. ВРУЧНУЮ провалидировать: открыть golden.jsonl и проставить
#    "accepted": true  — вопрос осмысленный, эталон соответствует источнику
#    "accepted": false — мусорный вопрос / эталон не из фрагмента (пара исключается)
#    Оставленный null означает «не проверено» — такие пары в прогон ПОПАДАЮТ.

# 4. Первый прогон = новая точка отсчёта
python3 tools/eval/run.py --label after-w5 --ui-url http://localhost:8787 \
    --limit 0

# 5. Поменять настройки (в UI: порог грейдера, rerank_candidates, промпт …)
#    и прогнать ВТОРОЙ раз на ТОМ ЖЕ golden.jsonl
python3 tools/eval/run.py --label threshold-3 --ui-url http://localhost:8787

# 6. Сравнить
python3 tools/eval/run.py --compare \
    tools/eval/reports/report-after-w5.json \
    tools/eval/reports/report-threshold-3.json
```

Дефолт `--ui-url` — `http://localhost:8787`, тот же порт, что печатает
`bootstrap.py` и слушает `run.sh` (раньше здесь стоял `8080`, и прогон без
флага уходил в пустоту). Другой адрес — флагом или через `COGNIVAULT_UI_URL`.

**Откуда берётся контекст для метрик.** По умолчанию харнесс читает
`~/.cognivault-ui/rag_log.jsonl` (флаг `--rag-log`, переменная
`COGNIVAULT_UI_RAG_LOG`) и берёт оттуда `context_text` — **ровно тот** блок
«Источники», который видела модель, вместе с `chunk_index` каждого источника и
снимком настроек хода. Если лога нет, включается фолбэк по метаданным, и весь
отчёт помечается **ПРИБЛИЖЁННЫМ** (см. ниже). В k8s лог лежит внутри пода:
```bash
kubectl cp <pod>:/data/rag_log.jsonl ./rag_log.jsonl
python3 tools/eval/run.py --label after-w5 --rag-log ./rag_log.jsonl
```

Отчёты складываются в `tools/eval/reports/` (в git не попадают, см. `.gitignore`).
`golden.jsonl` после ручной валидации имеет смысл закоммитить — прогоны сравнимы
только на одном и том же наборе.

## Схема `golden.jsonl`

По одной паре на строку, UTF-8 без экранирования кириллицы:

```json
{"id": "3f2a9c1b0d-f", "question": "Какой overlap у чанков?", "ground_truth": "Overlap отсутствует.", "kind": "factual", "category": "индексация", "source_path": "docs/indexing.md", "section_path": "Индексация > Чанкер", "source_chunk_index": null, "expected_refusal": false, "accepted": null}
```

| Поле | Тип | Смысл |
|---|---|---|
| `id` | string | `<sha1(path::section::текст)[:10]>-f` / `-p` — стабилен между перегенерациями |
| `question` | string | самодостаточный вопрос на русском |
| `ground_truth` | string | эталонный ответ 1–3 предложения, строго по фрагменту |
| `kind` | `"factual"` \| `"practical"` \| `"unanswerable"` \| `"meta"` | тип вопроса; следует ВЕРДИКТУ, а не теме |
| `category` | string \| отсутствует | **необязательная** ручная категория (тема вопроса). Отчёт строит по ней разрез `by_category`; пары без неё сходятся в `unclassified` |
| `source_path` | string \| `null` | путь документа-источника; `null` у вопросов без ответа в корпусе |
| `section_path` | string \| `null` | breadcrumb раздела `H1 > H2 > H3` |
| `source_chunk_index` | int \| `null` | номер чанка бэкенда. Генератор его не знает (режет корпус своим сплиттером) и пишет `null`; проставленный вручную, он поднимает `retrieval_hit` с уровня раздела до уровня **чанка** |
| `expected_refusal` | bool | `true` → правильный ответ — отказ; такая пара меряет ветку отказа и не участвует в `retrieval_hit` |
| `expected_outcome` | `"answer"` \| `"refusal"` \| `"meta"` | трёхзначный вердикт (введён 2026-08-01). Отсутствует — выводится из `expected_refusal`, поэтому старые наборы читаются как раньше |
| `accepted` | `true` \| `false` \| `null` | ручная валидация; `false` → пара не участвует в прогоне |

### Вопросы без ответа в корпусе (`expected_refusal`)

`gen_golden.py --unanswerable-share 0.12` (дефолт) просит модель придумать
правдоподобный вопрос по той же теме, ответа на который в документации нет.
Без этих пар ветка отказа не измеряется вообще: golden-set из одних отвечаемых
вопросов не покажет систему, которая на всё отвечает выдумкой. В отчёте они
дают строку `refusal_ok` — долю пар, где ассистент честно отказался.

**Их ручная валидация обязательна.** Модель придумывает вопрос вслепую, зная
один фрагмент; ответ может найтись в другом документе. Проверьте поиском и
поставьте `accepted: false` там, где ответ в базе всё-таки есть.

### Метавопросы (`expected_outcome: "meta"`)

Третий исход, потому что двух не хватало. Вопрос ПРО САМУ БАЗУ («что ты знаешь?»,
«о каких продуктах есть информация?», «из каких разделов состоит база») или про
ассистента («всегда ли ответ в Markdown?») устроен как ловушка — документа-цели
не существует, `source_path` пуст, `retrieval_hit` не считается, — но требует
ПРОТИВОПОЛОЖНОГО поведения: отвечать. Разметив такую пару как `expected_refusal`,
набор награждал бы отказ «в документах не нашлось», то есть ровно тот дефект,
который чинит итерация «метавопросы и перечисления по корпусу».

Ветку меряет `meta_answered_rate` — доля метапар, на которые ассистент ответил, а
не отказался (**больше — лучше**); пер-сэмпловый флаг — `meta_answered`. Судейские
средние метапар лежат в `aggregate_meta` и в `aggregate` не подмешиваются: без
размеченного контекста `context_precision`/`context_recall` мерили бы отсутствие
разметки. `expected_refusal` при этом НЕ переопределён — он остаётся флагом
ловушки, и `refusal_ok`, `false_refusal_rate`, `aggregate_refusal` считают ровно
то же, что считали.

Класс `corpus_scope` в `golden.corpus.jsonl` (строки `g500`–`g520`, `origin:
"authored"`) — перечисления по ВСЕМУ корпусу. Он распадается на те же исходы:
`answer` — список лежит на странице-контейнере; `meta` — список существует только
как форма дерева (страница «Продукты» в корпусе пустая); `refusal` — измерения,
которого в корпусе нет вовсе (SLA, владельцы, годы запуска), где верный ответ —
оговорка с ПРАВИЛЬНЫМ охватом, а не выдуманный список. Отрицательный контроль к
классу — `golden.control.json`: 56 уже отвечаемых ДОКУМЕНТНЫХ перечислений
(«перечисли все поля витрины X»), которые не должны получить оговорку.

### Парный набор `golden.vocab.jsonl` (`vocab_mismatch`)

35 ПАР, 70 строк (`pair_id` `v25` пропущен: пара была выброшена по замеру, см. ниже),
`origin: "authored"`, `category: "vocab_mismatch"`,
`expected_outcome: "answer"` у всех. Набор существует ради ОДНОГО вопроса: теряется
ли нужный документ, когда его спрашивают не той лексикой, какой он написан. Это
единственное, что он меряет, — и единственное, ради чего его стоит гонять.

Устройство. Каждый информационный запрос задан ДВАЖДЫ, с одним `pair_id`
(`v01`…`v36`) и одним и тем же gold-документом:

- `variant: "mismatch"` — как спросил бы коллега, страницу НЕ читавший: разговорно,
  синонимом, описанием потребности, по-русски там, где на странице английский
  термин (и наоборот), расшифровкой там, где на странице аббревиатура,
  пользовательским именем там, где на странице внутреннее;
- `variant: "matched"` — та же потребность словами самой страницы (заголовок,
  подзаголовки, тело).

Читается разность, не абсолют. `matched` находит, `mismatch` — нет ⇒ разрыв
лексический, и переписывание запроса имеет запас. Не находит ни один ⇒ вопрос просто
трудный, к словарю отношения не имеет. Находят оба ⇒ **запаса нет, и гипотезу
структурного переписывания запроса это ЗАКРЫВАЕТ**. Ноль промахов здесь — не провал
набора, а результат: `recall@40` на существующих наборах и так 188/188, и набор
собирался в полном ожидании такого исхода. Подгонять формулировки под промахи
нельзя — это превратило бы измерение в его имитацию.

Дополнительные поля (все аддитивные, старые загрузчики их игнорируют):

| Поле | Смысл |
|---|---|
| `pair_id` | общий ключ пары; ровно две строки на ключ |
| `variant` | `mismatch` \| `matched` |
| `mechanism` | `synonym` (8 пар), `abbreviation` (6), `ru_en` (6), `colloquial` (6), `paraphrase` (5), `alias` (4) — от механизма зависит цена лечения: словарь синонимов/алиасов чинит `alias` и `abbreviation` дёшево, `paraphrase` не чинит ничем дешёвым |
| `gold_paths` | `[source_path, *alt_source_paths]` одним списком — удобство парного раннера, ИСТИНА по-прежнему в `source_path`/`alt_source_paths`, их читает харнесс |
| `near_duplicates` | страницы, почти неотличимые от gold (реестры-близнецы, архивные копии). Заполнено у 8 пар; нужно, чтобы промах можно было отнести на `collapseCrossFileDuplicates`, а не на словарь |
| `near_duplicates_note` | почему они близнецы |
| `gold_evidence` | цитата из gold-документа, которой проверена разметка: ею — и только ею — обоснован ответ на ОБЕ строки пары |
| `lexical_overlap` | `{terms, rare_terms, rare_df_max, corpus_docs}` — сколько термов вопроса встречается в gold-документе |

`lexical_overlap` посчитан ПРОДОВЫМ токенизатором (`src/lib/bm25.ts` через мост
`tools/rag_audit/sparse_vectors.ts`: документы — `buildDocumentSparseVector`, вопросы
— `buildSparseVector`), а не второй реализацией на Python. `rare_terms` — сколько из
пересечения приходится на термы, встречающиеся не более чем в `rare_df_max = 8` из
127 документов корпуса; именно такие термы и решают исход лексической ветки.
У ВСЕХ 35 строк `mismatch` `rare_terms == 0`, у всех 35 `matched` `rare_terms ≥ 1`,
и `terms` у `matched` строго больше, чем у близнеца. Это и есть доказательство, что
пара хорошо сформирована: расходятся арки именно словарём, а не темой.

Выброшенная пара `v25` (gold — «Принципы работы моделей машинного обучения», модели
серии BNPL) не прошла этот же замер: страница на 85 КБ лексически настолько широка,
что любая пользовательская формулировка про рассрочку задевала её редкие термы
(`rare_terms == 4` у арки `mismatch`). Крупный документ поглощает произвольный
словарь, и «промах по словарю» на нём в принципе не наблюдаем — поэтому пара
удалена, а не переформулирована.

Границы. Офлайн-харнесс (`tools/rag_audit/audit_retrieval.py`) считает плотную
ветку ЛОКАЛЬНОЙ моделью-заменителем EmbeddingsGigaR, поэтому её числа на прод не
переносятся: локальная модель иначе переживает синонимию и русско-английские пары,
и промах/попадание плотной ветки офлайн — это свойство заменителя. Разреженная
ветка, наоборот, ПРОДОВАЯ до бита (тот же `bm25.ts`), так что вывод «BM25 теряет
документ на пользовательской лексике» переносится, а «hybrid теряет» — нет, пока не
померено на живом стенде. Набор также ничего не говорит о том, ОТВЕТИТ ли ассистент
правильно: `source_path` размечен на уровне ФАЙЛА (`section_path`,
`source_chunk_index` — `null`), меряется попадание документа в кандидатов, а не
качество генерации.

### Категории (`category`)

Поле необязательное и целиком ручное: `gen_golden.py` его не проставляет, а
строки без него работают как раньше. Смысл в том, что общее среднее по
разнородному набору прячет ровно то, ради чего набор и собирали руками: одна
тема просела, другая выросла, сумма не сдвинулась. Отчёт даёт разрез
`by_category` (и в JSON, и таблицей в markdown), а `--compare` — дельты по
категориям, которые есть в ОБОИХ прогонах.

Набор категорий берётся из данных. Если между прогонами он поменялся, диф
печатает, каких категорий не хватает в каком прогоне, и предупреждает, что раз
состав набора разъехался — общие средние и парная дельта тоже считаны по разным
вопросам. Молча выбросить такую категорию нельзя: это читалось бы как «её не
было».

«Сбои генерации» и список упавших пар.

Заголовок отчёта получает суффикс **«(РЕРАНКЕР НЕ РАБОТАЛ)»**, если грейдер
включён, а оценки вернулись меньше чем на 90 % применимых пар
(`grader_health.graded / applicable < 0.9`): это другая система, а не другая
настройка, и `--compare` с таким отчётом отказывается без `--allow-degraded`.

> **Сначала читайте «Скрытые вызовы», потом метрики.** Метрики описывают ответ;
> эта секция описывает пайплайн, который его собрал, — и если он собран не тем
> пайплайном, метрики нечего сравнивать. Два числа оттуда:
>
> * `grader_health` — на скольких парах грейдер вернул хоть одну оценку.
>   Провалившийся батч деградирует во все `None`, отбор пропускает кандидатов
>   в сыром порядке поиска, и прогон измеряет систему БЕЗ реранкера, ничем
>   этого не показывая. В прогоне `baseline` оценки были у 2 пар из 44.
> * `stage_timings` — медиана и максимум по стадиям рядом с их поводком
>   (`grader_timeout`, `condense_timeout` из снимка настроек хода). Время,
>   совпавшее с поводком, — таймаут, а не работа: в `baseline` стадия `grade`
>   стояла в 20003–20023 мс на 41 ходе из 46 при поводке в 20 с.
>
> Там же видно, вызывался ли condense: харнесс задаёт каждый вопрос в НОВОМ
> чате, поэтому при выключенном `condense_first_turn` переписывание вопроса не
> запускается ни разу, и из двух скрытых вызовов на ход меряется один. Строка
> «condense включён» это оговаривает.
>
> * `hidden_call_health` — ПОЧЕМУ грейдер (и condense) не отработал. UI пишет
>   в запись хода `hidden_calls`: исход каждого батча грейдера (`ok` / `failed`
>   / `truncated` / `partial`) с `error`, `detail`, `finish_reason`, `usage`,
>   моделью и временем. Отчёт сводит это в счётчики по исходу, по типу ошибки
>   (тип исключения + первые 120 символов сообщения, до трёх примеров `detail`
>   на тип), по `finish_reason` и по модели, — и первоэкранное предупреждение
>   «Грейдер молча не отработал» называет доминирующую причину: «Причина по
>   батчам: KitaiQueryFailed: 404 "No such model" (glm-5.1) — 160 батч(ей)».
>   Записи старого UI без `hidden_calls` ничего не додумывают: печатается
>   «Причина не записана: UI старее сбора скрытых вызовов», а в таблице по
>   парам колонка «грейдер» показывает `—` (иначе `ok`, `2/4 ✗`, `trunc`).

> **Судейские средние покрывают только отвечаемые пары.** Четыре метрики судьи
> в `aggregate` считаются по парам БЕЗ `expected_refusal`; ловушки вынесены в
> `aggregate_refusal`. Практическое следствие: `aggregate` двух прогонов
> сравним, только если совпадают ОБА числа из `buckets`. Диф это проверяет и
> предупреждает сам, а в шапке отчёта размеры обеих корзин напечатаны явно —
> чтобы прогон на 39 вопросах не сравнился незаметно с прогоном на 30.

`compare-<A>-vs-<B>.md` — таблица
`| Метрика | A (mean ±sd, n) | B (mean ±sd, n) | Δ (парная) | ±sd | пар | Знак |`:

* **Δ парная** считается по пересечению `id` обоих прогонов, а не как разность
  средних. Разность средних смешивает изменение качества с изменением состава
  оценённых пар (в одном прогоне судья не ответил на три вопроса, в другом — на
  другие три); парная дельта состав из уравнения убирает.
* **±sd и «пар»** показывают, из чего дельта сложена. Сдвиг 0.05 по 60 парам
  при sd 0.10 и тот же сдвиг по 6 парам при sd 0.4 — разные утверждения.
* **Знак** `▲`/`▼` ставится, только когда |Δ| больше И порога шума (0.02),
  И двух стандартных ошибок парной дельты; иначе `≈`. Раньше знак ставился по
  одной константе 0.02 без учёта разброса, и обычная дрожь судьи регулярно
  объявлялась регрессией.
* Диф предупреждает, если прогоны сделаны разными версиями судейских промптов,
  на разных golden-set, с разными параметрами прогона, с разным составом корзин
  (`buckets`) или если хотя бы один из них **приближённый**.
* Ниже общей таблицы идёт разрез **по категориям**: одна строка на категорию,
  которая есть в обоих прогонах, с дельтами по всем метрикам. Это разность
  СРЕДНИХ (не парная — внутри категории пар мало), и она слабее общей дельты.
  Категории, которые есть только в одном прогоне, перечисляются отдельным
  предупреждением, а не выбрасываются.
* **Отчёт, сделанный прежней версией харнесса** (без `by_category`,
  `aggregate_refusal`, `false_refusal_rate`), диф читает без падения: недостающие
  строки печатаются как `—`, а сверху появляется пометка, что его судейские
  средние посчитаны ВМЕСТЕ с парами-ловушками и потому не сопоставимы напрямую.

**Знак означает качество, а не направление числа.** У `false_refusal_rate` и
`hedge_rate` меньше — лучше, поэтому ▲ у них стоит при ПАДЕНИИ доли; в
остальных строках это одно и то же.

Обе секции «Параметры прогонов» печатаются целиком: модель и температура
отвечающей системы, ширина ретрива, порог грейдера, флаги, отпечатки промптов,
модель и версия промптов судьи. Прогоны сравнимы только при совпадении всего,
кроме того, что вы намеренно меняли.

### Метрики

| Метрика | Что считает | Как |
|---|---|---|
| `faithfulness_ru` | доля утверждений ответа, подтверждённых контекстом | ответ режется своим русским сегментатором на предложения, судья ставит 0/1 каждому |
| `answer_relevancy_ru` | отвечает ли ответ на заданный вопрос | судья ставит 1–5 → `(score-1)/4`; уклончивый ответ → 0 |
| `context_precision` | доля выданных фрагментов, релевантных вопросу | судья помечает каждый источник 0/1 |
| `context_recall` | покрыт ли `ground_truth` контекстом | эталон режется на предложения, судья проверяет выводимость каждого |
| `retrieval_hit` | считается локально, без судьи | попала ли пара `(source_path, source_chunk_index)` в выданные источники |
| `refusal_ok` | считается локально, без судьи | доля пар `expected_refusal`, где ассистент отказался вместо выдумки |
| `false_refusal_rate` | считается локально, без судьи. **Меньше — лучше** | доля ОТВЕЧАЕМЫХ пар, где ассистент отказался зря |
| `meta_answered_rate` | считается локально, без судьи. **Больше — лучше** | доля МЕТАПАР (`expected_outcome: "meta"`), на которые ассистент ответил, а не отказался |
| `hedge_rate` | считается локально по флагу судьи `answer_relevancy_ru.hedged`. **Меньше — лучше** | доля ОТВЕЧАЕМЫХ пар, где ответ по существу есть, но открывается оговоркой «прямого ответа не нашлось» (промпты v2 не обнуляют такой ответ — оценивают содержательную часть и поднимают флаг). В отчёте прежних промптов поля нет — `null`, не 0 |

Четыре судейские метрики считаются **только по отвечаемым парам**. Раньше пары
`expected_refusal` мерились теми же четырьмя метриками против эталона отказа, а
`answer_relevancy_ru` по построению ставит 0 уклончивому ответу — то есть
ПРАВИЛЬНЫЙ отказ тянул общее среднее вниз, и число зависело от доли ловушек в
наборе, а не от качества. Теперь их средние лежат в `aggregate_refusal`, а
осмысленная оценка ветки отказа — `refusal_ok`.

`false_refusal_rate` меряет обратную и более опасную ошибку: у вопроса ответ
есть, а пользователь получил «в источниках ничего нет». `refusal_ok` её не видит
вообще (он смотрит только на ловушки), и закручивание порога грейдера «улучшает»
`refusal_ok` ровно за счёт `false_refusal_rate`. Пер-сэмпловый флаг лежит в
`false_refusal` (у ловушек — `null`: там отказ и ожидался).

`retrieval_hit` — ключ к правилу диагностики из плана:
**нужный чанк был в контексте, а ответ неверен → чинить генерацию; не был →
чинить ретрив.**

Гранулярность падает вместе с полнотой golden-пары, и отчёт её печатает
(`retrieval_granularity`):

| Уровень | Когда | Что сравнивается |
|---|---|---|
| `chunk` | у пары есть `source_chunk_index` | `(path, chunk_index)` по `chunk_indexes` источника; блок `depth="file"` покрывает любой чанк своего файла |
| `section` | чанка нет, есть `section_path` | `(path, section_path)` |
| `file` | нет ни того, ни другого | только `path` — **завышает** hit: файл мог попасть в контекст совсем другим фрагментом |

Считается только по **успешным** парам: у упавшего сэмпла «не попали» означает
«прогон сломался», а не «ретрив промахнулся».

### Промпты судьи v2 — baseline v1 несопоставим

`metrics.PROMPT_VERSION = "v2"`: `answer_relevancy_ru` больше не ставит 0
ответу с оговоркой (флаг `hedged` → `hedge_rate`), у каждой метрики в `raw`
появились `calls` (сколько вызовов судьи ушло), `context_clipped_by_judge`
(судья видел контекст, урезанный СВОИМ капом) и `replies` (сырые ответы судьи
по вызовам). **Отчёты, снятые промптами v1, с v2 не сравниваются** — `--compare`
печатает блок «СУДИЛИ РАЗНЫЕ ВЕРСИИ ПРОМПТОВ» первым и завершается с кодом 2;
`--allow-model-mismatch` снимает и этот запрет (флаг один на оба случая, что
модели, что промпты), но правильный ход — перегнать старый baseline.

Что ещё из этого видно в отчёте:

* **кап судьи** — `counts.judge_context_clipped` и пер-сэмпловый
  `judge_context_clipped`: судья резал контекст сам (`metrics.format_context`),
  это ДРУГОЙ дефект, чем `context_clipped` (обрезка `context_text` в логе,
  `rag_log.MAX_TEXT_CHARS`). В шапке — строка «кап судьи: нет», иначе
  первоэкранное предупреждение со списком id.
* **счётчик вызовов** — `run_params.judge_calls_by_metric` (сумма `raw.calls` по
  метрикам и всего) и строка шапки «судейских вызовов: N (faithfulness a,
  relevancy b, precision c, recall d)». На «различаются параметры прогонов» этот
  счётчик не влияет.
* **`raw.replies` не сохраняется в отчёт**: перед записью `report-<label>.json`
  ключ выбрасывается из `raw` каждой метрики (`run.slim_report`,
  `REPORT_DROPPED_RAW_KEYS`) — это самое тяжёлое поле, десятки КБ на пару.
  Всё остальное (`score`, `raw.calls`, вердикты, `context_clipped_by_judge`,
  `hedged`) остаётся.

### Контекст: лог — норма, восстановление — аварийный режим

SSE-событие `sources` отдаёт только метаданные (`n, title, path, section_path,
score, depth`, + `url`/`grade`), самих чанков в нём нет. Поэтому источник
правды — `rag_log.jsonl`: UI пишет туда `context_text` (тот самый
отрендеренный блок «Источники»), `chunk_index`/`chunk_indexes` каждого
источника, `finish_reason`, тайминги стадий и снимок настроек. Харнесс режет
`context_text` обратно по заголовкам `### Источник N:` и отдаёт судье ровно то,
что видела модель.

Фолбэк (лога нет либо задан `--no-rag-log`) восстанавливает текст из
метаданных — и это **систематически смещает метрики В ОБЕ СТОРОНЫ**:

* блок с `depth="chunk"` подменяется ЦЕЛОЙ секцией — контекст богаче
  настоящего, `context_recall`/`faithfulness` завышаются;
* блок с `depth="file"` обрезается до первых `--context-chars` символов —
  контекст беднее настоящего, те же метрики занижаются.

Сдвиг зависит от состава `depth` в прогоне, поэтому он **не сокращается** при
сравнении: A/B между прогоном по логу и прогоном по метаданным недостоверен, и
A/B двух фолбэк-прогонов достоверен только пока состав `depth` не поменялся —
а он меняется ровно от тех правок ретрива, которые вы и меряете. Такой прогон
помечается `approximate: true`, в шапке отчёта и diff-таблицы печатается
предупреждение. Флаг `--no-context-fetch` отключает и дотяжку тоже (тогда
метрики по контексту бессмысленны).

### Упавшие пары исключаются из средних

Сэмпл получает `failed: true`, если чат вернул ошибку, оборвался транспорт или
текст контекста получить не удалось. Такие строки не участвуют **ни в одном**
среднем, ни в `retrieval_hit`, ни в парной дельте; их число печатается
отдельной строкой отчёта и списком «Упавшие пары». Раньше ошибка бэкенда давала
судье пустой контекст, нули уезжали в среднее и читались как регрессия
качества.

### Сбои генерации — отдельный исход, а не оценка

Пара с `empty_answer: true` в записи лога (или, у старых записей, с пустым
текстом при `finish_reason: "length"`) попадает в корзину `generation_failed`:
ответа не было вовсе, и это не отказ и не плохой ответ. Судья на неё **не
вызывается** (`metrics: null`, пометка в `metrics_note`), она не входит ни в
судейские средние, ни в `refusal_ok` / `false_refusal_rate` /
`meta_answered_rate`, ни в парную дельту `--compare`; `retrieval_hit` по ней
считается — ретрив состоялся. Число лежит в `counts.generation_failed` и в
строке корзин шапки («сбоев генерации: G»), список — в секции «Сбои генерации»
(id, `finish_reason`, время стрима, модель). Пустой поток при
`finish_reason: "no_context"` сюда НЕ попадает: это штатный отказ «грейдер ничего
не оставил», его меряет `refusal_ok`.

### Модель и провайдер — по факту

С появлением KitAI ключ `gigachat.model` в снимке настроек перестал быть
правдой: при `provider: kitai` отвечает `kitai_model`. Отчёт берёт
`settings.model_effective` (пишет UI), за неимением — `gigachat.provider` +
подходящий ключ модели, и только совсем старый снимок показывает `gigachat.model`
с пометкой «(ключ провайдера не записан)». Значения лежат в
`run_params.answer_provider` / `answer_model` / `answer_model_note`, печатаются
в шапке и в «Параметрах прогона». `--compare` при разных провайдерах или
моделях печатает громкий блок ПЕРВЫМ и отказывается (код выхода 2) без
`--allow-model-mismatch`; отчёт без записанной модели считается «не
проверяемым» — предупреждение есть, отказа нет.

### Дрейф путей golden

На старте прогона (если бэкенд доступен и не задан `--no-context-fetch`)
харнесс читает `GET /api/vault/catalog` целиком (постранично по
`limit`/`offset` до `total`) и сверяет с ним `source_path` и `alt_source_paths`
каждой golden-пары: точное совпадение — ок; нет совпадения, но ровно один живой
путь с тем же именем файла — он добавляется в эффективные `alt_source_paths`
пары на время прогона (`path_drift: {golden, live}`), и `retrieval_hit`
считается по ним; несколько кандидатов — `path_ambiguous: [...]`, ничего не
подставляется; ни одного — `path_missing: true`. Сводка — `path_drift` в JSON,
секция «Дрейф путей golden» и первоэкранное предупреждение в markdown; сама
разметка `golden.jsonl` не переписывается — поправьте её руками. Каталог
недоступен или пуст — одно предупреждение в лог, поведение как раньше.

### GigaChat (судья и генератор вопросов)

|---|---|---|
| `GIGACHAT_BASE_URL` | да* | напр. `https://gigachat-ift.sberdevices.delta.sbrf.ru/v1` |
| `GIGACHAT_CERT_PATH` | да | клиентский сертификат PEM — это и есть аутентификация (bearer-токена нет) |
| `GIGACHAT_KEY_PATH` | да | приватный ключ PEM |
| `GIGACHAT_KEY_PASSPHRASE` | нет | пароль ключа (тогда клиент строит `ssl.SSLContext`) |

| `GIGACHAT_VERIFY_SSL` | нет | `true`/`false`; по умолчанию берётся из config.json |
| `GIGACHAT_MODEL` | да* | модель по умолчанию (та же, что в чате) |
| `EVAL_JUDGE_MODEL` | нет | **переопределяет** модель-судью поверх всего остального |

## Требования к контуру

* Клиентские **mTLS-сертификаты** GigaChat (`*.crt` + `*.key`) должны лежать на
  машине, откуда запускается харнесс, и быть доступны на чтение. Без них
  `gen_golden.py` и `run.py` падают сразу с `GIGACHAT_CERT_MISSING`
  (чистые функции модулей при этом остаются работоспособны — тесты офлайн).
* Сеть до GigaChat (VPN/корпоративный контур), до бэкенда и до UI.
* Вольт **проиндексирован** — иначе `sources` будут пустыми и все метрики уедут в 0.
* Стоимость прогона: ~4 судейских вызова на пару (+1 генерация на фрагмент).
  80 пар ≈ 320 вызовов — и все они идут **последовательно**: `--concurrency`
  выше 1 упирается в 429 (у судьи фактически один слот), а ретраи короче чужого
  вызова, поэтому проигравший теряет метрики целыми сэмплами.

## CLI

```
gen_golden.py --out PATH --limit N --seed N --base-url URL --token TOKEN --dry-run
              [--concurrency N] [--max-chars N] [--min-chars N] [--ext .md,.txt]
              [--unanswerable-share 0.12] [--config PATH]

run.py --golden PATH --label NAME --ui-url URL --token TOKEN --limit N
       --concurrency N --out-dir DIR
       [--rag-log PATH] [--no-rag-log]
       [--include-rejected] [--backend-url URL] [--backend-token TOKEN]
       [--no-context-fetch] [--context-chars N] [--config PATH]
run.py --compare A.json B.json [--out-dir DIR]
       [--allow-model-mismatch] [--allow-degraded]
```

`--compare` завершается с кодом 2 и не пишет диф, если в прогонах отвечали разные
модели/провайдеры или судили разные версии промптов (`--allow-model-mismatch`
снимает оба запрета) или если хотя бы в
одном из них реранкер не работал — грейдер оценил меньше 90 % применимых пар
(`--allow-degraded`).

## Тесты

```bash
python3 -m compileall -q tools/eval

```

Тесты полностью офлайн: GigaChat и REST мокаются через `httpx.MockTransport`,

разбор JSON (```json-обёртка, преамбула, битый), агрегация метрик, генерация
diff-таблицы, markdown-сплиттер и форма строк golden.jsonl, а также правки

лога не дёргается), исключение упавших сэмплов из всех средних, `retrieval_hit`
по паре `(path, chunk_index)` с деградацией до раздела/файла, парная дельта с
разбросом и числом пар, ветка отказа, разрез по `category` (включая пары без

`slim_report` (без `raw.replies`) и отказ `--compare` при разных версиях промптов.

## Что менять осторожно

Промпты судьи (`metrics.py`) версионируются `PROMPT_VERSION`. Меняете промпт —
**поднимайте версию**: старые отчёты после этого несравнимы с новыми, и
`--compare` об этом предупредит.
